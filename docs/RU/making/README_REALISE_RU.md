# Remedia 1.2.0 — порядок выпуска

Выполняйте команды из корня рабочего репозитория Remedia. Отмечайте шаг только после проверки результата. Публикуйте тег и GitHub Release после успешной проверки собранного пакета.

## 1. Проверить `CHANGELOG.md`

- [ ] Просмотреть весь раздел `## [Unreleased]` и сверить каждое утверждение с реализованным и протестированным кодом. Удалить планы и неподтверждённые результаты; проверить, что исправления MediaPanel, экспорта и документации описаны верно.
- [ ] Перенести готовые записи под `## [1.2.0] - YYYY-MM-DD` (фактическая дата выпуска). Оставить пустой `## [Unreleased]` для следующих изменений. Не менять текст прошлых релизов без необходимости.
- [ ] Проверить ссылки на версии внизу changelog, если они есть: `Unreleased` должен начинаться от `v1.2.0`, а `1.2.0` сравнивать `v1.1.0...v1.2.0`.

```bash
sed -n '1,180p' CHANGELOG.md
git diff -- CHANGELOG.md
```

## 2. Найти все источники номера версии

- [ ] Найти текущую версию в CLI, скриптах, установщике, сборке Debian, тестах и документации. Отличать действующие значения версии от исторических упоминаний 1.1.0 в changelog и инструкциях.
- [ ] Обновить источники версии до `1.2.0`. Если номер хранится в нескольких местах, сверить их между собой; не менять номера внешних зависимостей или версий формата данных автоматически.
- [ ] Убедиться, что исходный пакет и собранный `.deb` выводят одну и ту же версию.

```bash
rg -n --hidden -g '!.git' '(^|[^[:digit:]])v?1\.1\.0([^[:digit:]]|$)|(^|[^[:digit:]])v?1\.2\.0([^[:digit:]]|$)|VERSION|Version:' .
git diff --check
```

Если последняя команда ничего не выведет, проверка прошла.

### Удаление пробелов
В GNOME Text Editor пробелы в конце строки обычно не видны. Их можно подсветить поиском:
1. Откройте файл и нажмите Ctrl+F.
2. В настройках поиска (значок шестерёнки) включите регулярные выражения.
3. Найдите [ \t]+$ — это пробелы или табуляции непосредственно перед концом строки. Редактор поддерживает поиск по регулярным выражениям.

## 3. Проверить исходники и поведение

- [ ] Посмотреть `git status --short` и `git diff --stat`; исключить личные медиафайлы, кэш, журналы и временные результаты.
- [ ] Проверить синтаксис изменённых Bash-файлов (`bash -n путь/к/файлу.sh`). Для файлов, которые только подключаются через `source`, это проверяет синтаксис, но не поведение.
- [ ] Запустить имеющиеся тесты проекта и записать команды и итог. Проверить MediaPanel на тестовом проекте: создание/открытие video и short MLT, экспорт, выбор одного/нескольких файлов для YouTube, повторное использование JSON и отмену пустым выбором.
- [ ] Проверить обе ветки экспорта, которые заявлены как поддерживаемые: CPU и NVENC; для Flatpak Shotcut — совместимость с установленным NVIDIA runtime. Не считать один успешный экспорт проверкой всех режимов.
- [ ] Проверить `README.md`, ROADMAP и инструкции по установке на соответствие фактическому 1.2.0 и схеме каталогов `video/`, `short/`, `export/`.

```bash
git status --short
git diff --stat
git diff --check
```

## 4. Собрать и проверить пакет

- [ ] Выполнить штатную команду сборки из репозитория (посмотреть `./DEBIAN/build.sh` или существующую инструкцию `README_DEBIAN_WORK_EN.md`; не подменять её произвольной командой).
* После сборки .deb-пакета никакие изменения в исходных скриптах уже не допускаются. Закончите релиз как есть.
- [ ] Проверить метаданные, состав и зависимости полученного `.deb`.
- [ ] Установить пакет в тестовой среде либо по своему обычному процессу обновления; проверить запуск `remedia`, `remedia setup`, `remedia doctor` и MediaPanel, затем чтение версии и сохранность пользовательского состояния.
*  Проверка установленной версии (`remedia --version`, `remedia-doctor --version` и подобные команды) применяется только если соответствующая команда действительно поддерживается проектом. Для Debian-пакета источник истины — поле `Version` в его `control`.
- [ ] Чтобы сохранить контрольную сумму рядом с .deb, перейдите в каталог с пакетом и выполните:

```bash
sha256sum path/to/remedia_1.2.0_all.deb > SHA256SUMS
cat SHA256SUMS
```

- [ ] Выполните проверки:

```bash
dpkg-deb -f path/to/remedia_1.2.0_all.deb Package Version Architecture Depends
dpkg-deb -c path/to/remedia_1.2.0_all.deb | less
sha256sum path/to/remedia_1.2.0_all.deb
```

Замените `path/to/` на действительный путь после сборки. Если имя или архитектура отличаются, используйте фактические значения и разберитесь с причиной расхождения до выпуска.
- [ ] Резервные .bak-* и .back можно удалить после проверки исправленных скриптов.

## 5. Зафиксировать выпуск в Git

- [ ] Проверить ветку и чистоту изменений: `git status --short`, `git branch --show-current`, `git diff`.
- [ ] Закоммитить подготовленный релиз; убедиться, что `CHANGELOG.md` и все версии уже обновлены.
```bash
git add -A
git diff --cached --stat
git diff --cached --check
git commit -m "Release Remedia 1.2.0"
```

- [ ] Проверить отсутствие существующего тега `v1.2.0`.

```bash
git status --short
git tag -l v1.2.0
git log -1 --oneline
```

Если тег уже существует, сначала выясните, на какой коммит он указывает. Не перезаписывайте опубликованный тег.

- [ ] Создать аннотированный тег на релизном коммите и проверить его цель.
```bash
git tag -a v1.2.0 -m "Remedia 1.2.0"
git log -1 --oneline
git show -s --format='%h %s' 'v1.2.0^{commit}'
git show --no-patch --decorate v1.2.0
```

Последние две команды должны показывать новый коммит 1.2.0 с одним и тем же хешем. Лишь затем отправляйте ветку и тег и оформляйте релиз на сайте

## 6. Опубликовать на GitHub

- [ ] Перед отправкой выполните git status --short: в нём не должно быть забытых изменений.
- [ ] Проверьте целевую ветку `origin` перед отправкой. Публикация релиза и загрузка пакета выполняются после всех отмеченных проверок.
- [ ] Можно отправлять:
```bash
git push origin main
git push origin v1.2.0
```
- [ ] Откройте страницу создания релиза: `github.com/krashevski/remedia/releases/new`.
- [ ] В Choose a tag выберите **существующий v1.2.0.Создать GitHub Release** . Заголовок: `Remedia 1.2.0`. Добавьте описание из `CHANGELOG.md`. отдельно выделив заметные изменения и инструкции обновления, если они нужны.
- [ ] Прикрепить проверенный `.deb` и файл SHA-256 либо указать хеш в заметках выпуска. Сверить пакет на странице релиза с локально проверенным файлом.
- [ ] Проверьте черновик и нажмите Publish release.
- [ ] После публикации проверить ссылку на релиз, скачивание пакета и совпадение `Version: 1.2.0`.
